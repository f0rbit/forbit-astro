Plan: Terminal redesign + lint adoption + perf safe-wins

todo

A three-workstream initiative on the forbit-astro personal portfolio (Astro 4 SSR on Cloudflare Workers). (1) Adopt the @f0rbit/lint toolchain and land a clean baseline reformat BEFORE any redesign, so the "fix all lint/formatting" requirement is satisfied continuously. (2) Restyle every page into the "Turn 2 · Tokyo Night, restrained" terminal direction — a shared terminal-window shell (titlebar + traffic lights + path-nav) at the layout level, plus per-page redesign of home, projects, about, blog, timeline, project-detail and blog-post, and a mobile responsive pass. (3) Fold safe TTFB wins into the redesign phases and add a dedicated perf phase + a written docs/perf-ttfb.md analysis. Scope is a restyle: the data/provider layer and component data contracts stay intact.

Root cause

Stated goal: Adopt @f0rbit/lint, restyle the whole site to the terminal mockup, and implement safe TTFB wins + a perf report.

Underlying need: A portfolio that (a) reads as "this person builds developer tools" through a coherent terminal aesthetic on every surface, (b) has an enforced, single-source code-quality baseline so future changes stay clean, and (c) is fast to first byte on Workers without an SSR re-architecture.

Why this matters: Doing the restyle before the lint baseline would bury a repo-wide reformat inside redesign diffs, making review impossible and the "fix formatting" requirement a moving target. Splitting the terminal chrome per-page (instead of a shared shell) would duplicate the titlebar/path-nav five-plus times — the single-source-of-truth smell. And spreading the Tokyo Night palette as inline OKLCH across every component (as the mockup does) would make the theme un-maintainable. The ordering and the shared-shell / single-token-layer decisions ARE the substance of this plan.

Alternatives considered — where the Tokyo Night terminal tokens live

The redesign's one genuine architectural decision. Everything else (shell placement, page mapping, perf wins) is fixed by the brief. The current design tokens are OKLCH custom properties defined in the external @f0rbit/ui package (node_modules/@f0rbit/ui/src/styles/tokens.css), imported via Page.astro's import "@f0rbit/ui/styles". src/global.css already overrides a handful of @f0rbit/ui tokens/classes (.badge, .card). The site's components consume semantic tokens (--bg, --fg, --fg-muted, --fg-faint, --border, --accent, --space-*, --text-*, --radius). We must not edit node_modules.

Option 1: In-repo terminal token layer — one :root file overriding @f0rbit/ui semantic tokens

recommended

Add a single new in-repo file src/styles/terminal.css that (a) re-points the @f0rbit/ui semantic tokens the components already use (--bg→oklch(19% 0.03 274), --fg→oklch(97% 0.015 270), --fg-muted→oklch(72% 0.016 274), --border→oklch(31% 0.035 270), --accent→oklch(70% 0.12 258), etc.) to the Tokyo Night ramp, and (b) declares terminal-specific tokens the mockup needs but the library lacks (--term-panel, --term-titlebar, --term-border, --term-prompt-user green oklch(74% 0.11 150), --term-link blue, --term-keyword purple oklch(71% 0.11 300), --term-gray-30/45/58/72/85/97, --font-mono). Imported once in Page.astro immediately after @f0rbit/ui/styles, so the cascade overrides cleanly. The palette lives in exactly one place; every component reads it via tokens.

Real-world examples

  • GitHub Primer — ships base primitives, and product surfaces re-theme by overriding the same CSS custom properties in a downstream :root layer rather than forking Primer. source
  • Radix Themes / shadcn-ui — components consume semantic CSS variables (--background, --foreground, --border); a project retints the whole app by redefining those variables in one root stylesheet. source

Pros

  • Single source of truth for the palette: one file, one :root block. Change a hue once, every page updates.
  • Zero cross-repo blast radius — @f0rbit/ui stays generic; devpad and other consumers are unaffected.
  • Components already read semantic tokens, so most restyle work is "point tokens at Tokyo Night," not per-component rewrites.
  • Keeps the palette OUT of global.css (which holds element/type rules) — clean separation: terminal.css = colour/theme, global.css = element styles.

Cons

  • Terminal-specific tokens (prompt-user green, keyword purple, gray ramp) have no @f0rbit/ui equivalent, so they're net-new names — a small vocabulary to document in AGENTS.md.
  • Overriding library tokens means a future @f0rbit/ui token rename could silently drop an override — mitigated by a comment block listing which upstream tokens we shadow.

Architecture decisions

  • Token location: Option 1 (in-repo src/styles/terminal.css). See alternatives.
  • Terminal chrome is a shared Layout-level shell. A single TerminalWindow.astro renders the rounded panel, titlebar (3 traffic-light dots + centered forbit@dev — <path> — zsh + right-aligned path-nav tabs). Every page inherits it via Page.astro; the active path and titlebar text derive from Astro.url.pathname (mapping: /→~/home, /projects→~/work, /about→~/about, /blog→~/blog, /timeline→~/timeline; detail routes show ~/work/<id> etc.). This keeps the chrome defined once — no per-page duplication.
  • Path-nav is a rename of existing nav, not a new nav. The five path tabs map 1:1 to the five existing routes; no nav items added or removed.
  • Page-vs-integrate gate: This initiative adds zero net-new pages and zero net-new nav items — it restyles the seven existing routes in place. The gate is therefore satisfied trivially: no aggregation/feed page is introduced, and every datum stays on the page where the user already expects it. (Recorded here per the guidelines even though no new surface is created.)
  • Restyle, not refactor. The Provider/DI data layer (middleware.ts, providers/*, lib/cache.ts, in-memory fakes) and all component data contracts (props) are untouched. Tasks change markup/CSS and the two perf-relevant server behaviours (cache blog HTML, prerender evaluation) only.
  • Prompt-line primitive. PromptLine.astro renders forbit@dev:<path>$ <cmd> with the green user / gray path / optional blinking █ cursor, so the $ whoami / $ ls --featured / $ git log framings are consistent across pages.
  • UI primitives: Every redesign task MUST WebFetch https://f0rbit.github.io/ui/llms.txt first and reach for @f0rbit/ui primitives/utilities natively — layout via .row/.stack/.grid/.cluster, Card/CardContent, Badge/Status, Stat, Clamp, Empty, Collapsible — rather than reinventing wrappers. The terminal look comes from the token layer + a thin chrome component, not from replacing the primitives.
  • Perf wins split: moment→native and font preload fold into Phase 2 (they touch shared utils.ts + Page.astro head, already in flight there). Client-directive tuning, astro:assets, drizzle removal, prerender evaluation, and blog-HTML caching are the dedicated Phase 5, alongside the written report. Aggressive rework (wholesale SSR→static, cache-header redesign) is report-only in docs/perf-ttfb.md.
  • Visual verification gotcha: the chrome-devtools/playwright MCP is misconfigured (expects chromium-1217, 1223 is installed). Visual tasks should run bunx playwright install chromium (or point at the installed 1223 build), or fall back to astro build + astro preview + a manual screenshot. Load the visual-review skill for screenshot judgement.
