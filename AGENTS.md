# AGENTS.md — forbit-astro

Project-specific conventions and gotchas for agents working in this repo. Stacks on top of the global `~/.claude/AGENTS.md`.

## Lint/format toolchain

Code quality is enforced by `@f0rbit/lint` (oxlint + type-aware ESLint + oxfmt), not prettier.

- Scripts: `bun run lint`, `bun run lint:fix`, `bun run fmt`, `bun run fmt:check`.
- Config: `.oxlintrc.json`, `.oxfmtrc.json`, `eslint.config.ts`.
- `eslint.config.ts` calls `define_lint_config({ naming: "snake_case", tsconfig_root_dir: import.meta.dirname, module_resolution: "bundler", ambient_effect_files: ["src/lib/cache.ts", "src/lib/time.ts", "src/components/blog/PublishTime.tsx"], oxlintrc_path: ..., overrides: [...] })`.
- Format is tabs + 120 width (oxfmt defaults) — NOT the old prettier config (160 width, no semicolons, single quotes). The prettier→oxfmt swap is a breaking formatter change; the repo-wide reformat landed as a standalone Phase 1 commit before any redesign work, so later diffs stay clean.
- `.prettierrc` is deleted; `prettier` and `prettier-plugin-astro` are removed from `package.json`.
- Naming convention: `snake_case` for local variables/functions, `PascalCase` for types/components. **Provider interface methods stay camelCase** (e.g. `listProjects`, `getProject`, `listMyArticles`, `fetchTimeline`) — these are external API contract shapes (`@devpad/api`-style), not free-standing local identifiers, so the naming-convention rule does not (and should not) rename them.

### oxfmt does not format `.astro` files

`oxfmt` only formats `ts/tsx/js/jsx/json/etc` — it does **not** reformat `.astro` files. `.astro` files keep their existing formatting (tabs, quote style, etc. as originally authored) even after `bun run fmt`. Don't expect `fmt:check` diffs inside `.astro` frontmatter/markup from formatting-only issues.

### `.astro` / Solid `.tsx` ESLint coverage

`@f0rbit/eslint-config` only wires up `ts/tsx/mts/cts` extensions, and this repo does not install `astro-eslint-parser`. Consequence: **type-aware ESLint rules never see `.astro` file content** — there was never anything to explicitly "exclude." `oxlint` still lints inside `.astro` frontmatter (e.g. `unicorn/filename-case`, `typescript/no-explicit-any`), so `.astro` files aren't lint-free, just not covered by the _typed_ ESLint layer. Solid `.tsx` files (`SkillBars.tsx`, `SkillDetail.tsx`, `SkillCard.tsx`, `PublishTime.tsx`) go through the normal `ts_files` typed-ESLint path like any other `.tsx`.

### `oxlintrc_path` must point at the canonical oxlint config, not the repo's `.oxlintrc.json`

`eslint-plugin-oxlint`'s rule-dedupe (avoiding double-reporting between oxlint and ESLint) mirrors whatever `files` patterns it finds in the oxlint config it's pointed at. This repo's own `.oxlintrc.json` adds `files`-scoped overrides for `**/*.astro` (to turn off `unicorn/filename-case` there). If `oxlintrc_path` in `eslint.config.ts` pointed at `.oxlintrc.json` directly, the dedupe plugin would inject an ESLint flat-config object scoped to `**/*.astro` — and merely having an `.astro` `files` pattern anywhere in the flat config array makes plain `eslint .` try to parse `.astro` files with the default (non-Astro) parser, which fails immediately with a parse error. Fix: point `oxlintrc_path` at the **canonical** `@f0rbit/oxlint-config/oxlintrc.json` package export (via `createRequire(import.meta.url).resolve(...)`), which has no astro-scoped overrides, so the dedupe stays scoped to `ts_files` as intended. See `eslint.config.ts:24-36`.

### Infra file ignores

`infra.ts`, `pipeline.ts`, `grants.ts` (the pattern used elsewhere in the user's devpad/pipelines stack for files excluded from the TS program) **do not exist in this repo** — there was nothing to ignore for Phase 1. If they're added later (e.g. an Alchemy IaC file), add them to both the ESLint `overrides[].ignores` and mirror in `.oxlintrc.json`, matching the pattern already used for `.astro/**`, `.wrangler/**`, `worker-configuration.d.ts`.

### Scoped lint disables

Every `oxlint-disable-next-line` / `eslint-disable` in this repo carries a reason comment and points at a genuine pre-existing gap — not a convenience silence for something the lint-adoption pass introduced. Current instances: `get_timeline` in `src/utils.ts` (pre-existing `any` params, `@todo fix typings`), untyped `@devpad/api`/dev.to response shapes in `src/providers/*.ts` and `src/lib/build-data.ts`, the Astro middleware's mandated `onRequest` export name, and the ambient `Date.now()`/`new Date()` effects in `src/lib/cache.ts`, `src/lib/time.ts`, and `src/components/blog/PublishTime.tsx` (documented via `ambient_effect_files` in `eslint.config.ts` rather than a disable). Don't add a new disable to silence a rule you tripped — fix it, or defer it explicitly with the same reason-comment convention.

### `fmt:check` ignores `.plans/**`, but not markdown

`.oxfmtrc.json` sets `"ignorePatterns": [".plans/**"]` — plan HTML documents under `.plans/` are working artifacts with their own hand-rolled structure (they're rendered as pages, reviewed in a browser, and follow the canonical `plan-html-template`), not source to be reformatted. `AGENTS.md` (this file) is **not** ignored — oxfmt formats markdown cleanly; the only change it makes is normalizing `*emphasis*` to `_emphasis_`, which is safe. If a future oxfmt run on a markdown file produces a diff that looks like it's mangling content (not just whitespace/emphasis-style), re-evaluate whether that file should move to `ignorePatterns` instead of being auto-formatted.

## Terminal redesign (Tokyo Night theme + shared shell)

- **Design tokens — single source of truth:** the entire palette lives in `src/styles/terminal.css`'s `:root` block. It is intentionally **not** wrapped in `@layer` — `@f0rbit/ui` declares `@layer reset, tokens, components, utilities;` and puts its semantic tokens inside `@layer tokens`; per the CSS Cascade Layers spec, an unlayered rule always beats every layered rule regardless of import order or specificity, so `terminal.css`'s overrides win unconditionally. Shadowed upstream `@f0rbit/ui` tokens: `--bg`, `--bg-alt`, `--border`, `--fg`, `--fg-muted`, `--fg-subtle`, `--fg-faint`, `--accent`, `--font-mono`. Net-new `--term-*` vocabulary: `--term-panel`, `--term-titlebar`, `--term-border`, `--term-border-inner`, `--term-gray-{30,45,58,72,85,97}`, `--term-prompt-user`/`--term-status-finished` (green), `--term-link`/`--term-status-dev` (blue), `--term-keyword` (purple). Never inline an `oklch(...)` literal in a component — add a token to `terminal.css` instead. No webfont: the mono stack is 100% system fonts, so there's no `@font-face`/preload.
- **Shared terminal shell:** `src/lib/path-nav.ts` is the single source of the route→path map (`PATH_TABS`, `is_active_path`, `derive_path`), consumed by `Navigation.astro` (path-nav tab strip + mobile path menu, built on astro-navbar's `Astronav`/`MenuIcon`/`MenuItems`) and `TerminalWindow.astro` (titlebar chrome — traffic-light dots, centered `forbit@dev — {path} — zsh`, right-aligned `<Navigation/>` — defaults `path` to `derive_path(Astro.url.pathname)`). `PromptLine.astro` is the `forbit@dev:<path>$ <cmd>` primitive. `Page.astro` renders every route's content inside `<TerminalWindow>`; SEO/OG/JSON-LD head is untouched.
- **Double nav — resolved:** all 7 route files (`index`, `projects`, `projects/[project_id]`, `about`, `blog`, `blog/[group]/[slug]`, `timeline`) had their redundant page-level `<Navigation/>` calls removed as part of each page's Phase 3 restyle. `TerminalWindow.astro` is now the single place `<Navigation/>` is rendered — verify with `grep -rln "Navigation" src/pages/ src/components/`, which should only match `TerminalWindow.astro`.
- **All pages restyled to the terminal theme (Phase 3):** Home (`src/pages/index.astro`), Projects list + detail (`src/pages/projects.astro`, `src/pages/projects/[project_id].astro`, `ProjectCard.astro`, `components/projects/{ProjectPage,Status}.astro`), About (`src/pages/about.astro`, `components/about/{AboutMe,Experience,ExperienceCard,SkillEvents}.astro`, `components/about/{SkillBars,SkillDetail,SkillCard}.tsx`), Timeline (`src/pages/timeline.astro`, `components/activity/{Timeline,CommitList}.astro`), and Blog list + post (`src/pages/blog.astro`, `src/pages/blog/[group]/[slug].astro`, `components/blog/{BlogCard,RecentBlogs}.astro`) all compose `TerminalWindow`/`PromptLine`/`--term-*` tokens natively — no re-declared chrome, no inline color literals. These were built in parallel worktrees on disjoint file sets and squash-integrated into one commit with zero conflicts.
- **`Experience` variant consolidated:** `Experience.astro`'s `mode` prop was collapsed from a multi-variant union down to a single `mode: "left"` literal (left-border timeline layout) — the only variant either caller (`index.astro`, `about.astro`) used. Widen back to a union if a second layout is ever needed.
- **Lint/format ignores nested worktrees:** `.claude/worktrees/**` (created by parallel `coder-fast` agents) is untracked but not gitignored and lives inside the repo tree, so `oxlint .`/`eslint .`/`oxfmt --check .` from the main tree recursed into sibling worktree checkouts and failed on their differently-versioned toolchains. Fixed by adding `.claude/**` to `ignorePatterns` in `.oxlintrc.json` and `.oxfmtrc.json`, plus an `ignores: [".claude/**"]` override in `eslint.config.ts`. Note: a `src/lib/build-data.ts` unused-eslint-disable failure reported by all five Phase 3 worktrees did **not** reproduce on the main tree's canonical `node_modules` — it was a worktree-local artifact (stale/mismatched installed lint package versions in freshly-bootstrapped worktrees), not a real regression. If it resurfaces on the main tree, treat it as real and fix `src/lib/build-data.ts:21,23`.
- **`astro preview` doesn't work with the Cloudflare adapter:** `@astrojs/cloudflare` explicitly rejects the `astro preview` command. For local visual checks, `bun run build` then `bunx wrangler dev --port 8788` (reads `wrangler.jsonc`'s `assets` binding + `.dev.vars`). If the chrome-devtools MCP's pinned Chromium revision doesn't match what's installed, `bunx playwright install chromium` and drive a small standalone Playwright script instead.
- **Dates — moment.js removed:** replaced by `src/lib/time.ts` (native `Intl` + ms math): `format_duration(start, end)`, `format_relative_time`, `format_calendar`, `format_full_date_time`. Re-exported from `src/utils.ts` as `format_duration` for existing callers. Client-safe (zero deps), so `PublishTime.tsx` (a Solid client island) no longer ships moment to the browser. **Deliberate behavior fix:** old `PublishTime.tsx` used moment's `calendar({ sameElse: "DD/MM/yyyy" })` — lowercase `yyyy` is an invalid moment format token, so it silently rendered the literal string `"DD/MM/yyyy"` for dates more than a week away. The replacement `format_ddmmyyyy` renders a real formatted date — a corrected bug, not a regression.

## Mobile responsive pass (Phase 4)

- **Breakpoint strategy — reuse, never invent:** ~~every responsive rule in this repo keys off the four breakpoints already established by `global.css`'s `.page-container` (640 / 1024 / 1280 / 1700)~~ **outdated as of the redesign polish pass** — `.page-container`'s escalating 640/1024/1280/1700 padding scale was removed (see "Single content-width container" below); it's now a single `clamp()`-based `padding-inline` with no discrete breakpoints. The still-current part of this rule: `@f0rbit/ui`'s own `.grid-2/-3/-4` mobile collapse at `max-width: 768px` is an existing upstream breakpoint, reuse it rather than inventing new ones. `AboutMe.astro` also has a `max-width: 1023px` breakpoint (mirroring its own pre-existing `min-width: 1024px` two-column switch) — reuse that one for anything scoped to the about-page two-column layout.
- **Grid overflow class of bug — `1fr` tracks don't shrink below content min-width:** any CSS grid track written as bare `1fr` (or `auto 1fr`) sizes its minimum to the content's min-content width by default. Wide, unwrappable card content (long tag lists, badges) can then force the track wider than its share of the container, overflowing a parent with `overflow: hidden` (e.g. `.terminal-window`) even though the _page_ never scrolls. Fix pattern: `minmax(0, 1fr)` on every `fr` track that holds card/component content, so the track can shrink and let the content's own wrapping (`flex-wrap`, text reflow) take over. Fixed at: `global.css`'s `.grid-2/-3/-4` override (covers `projects.astro`'s `grid-3`, `about.astro`'s `grid-3`/`grid-4`), `index.astro`'s `.recent-columns` (the desktop bug — `ExperienceCard` clipped on the right edge of the home page's two-column git-log/experience section), `blog.astro`'s `.blog-layout`, `ProjectPage.astro`'s `.project-body`, `AboutMe.astro`'s `.about-me`. When adding a new multi-column grid, default to `minmax(0, 1fr)` rather than bare `1fr` unless the track is a genuinely fixed non-shrinking width (e.g. a sidebar's `280px`).
- **Mobile menu overlay must not be positioned relative to the hamburger button:** `Navigation.astro`'s `.path-menu` (the full-screen `$ cd ~/` mobile menu) is `position: fixed; inset: 0` — NOT `position: absolute` scoped to `.mobile-menu` (the hamburger's own tiny wrapper). An absolutely-positioned overlay inside `.mobile-menu` inherits that element's narrow box as its containing block and renders as a sliver pinned to the button, not a full-screen panel. Because the fixed overlay is a DOM descendant of `.terminal-titlebar` (Navigation renders inside the titlebar), and `.terminal-titlebar` is a positioned ancestor with its own stacking context, the overlay's `z-index` is compared against the titlebar's _other children_ (dots, the menu-icon button) within that same local stacking context — not against the titlebar as a whole. So keeping the toggle button (and the traffic-light dots) visible/clickable above the open menu requires those specific elements to carry a higher `z-index` than `.path-menu` (`.terminal-dots` and `.menu-icon` are `z-index: 21` vs `.path-menu`'s `20`, both `position: relative`), not just raising the titlebar's z-index. If you touch this stacking again, verify with an actual screenshot at 360px with the menu open — the sliver bug (menu confined to the button's own hit-box) is easy to reintroduce and easy to miss without visually opening the menu, since layout/typecheck/build all pass regardless.
- **Timeline heatmap on mobile:** wrapped in a `.heatmap-scroll { overflow-x: auto }` container so it degrades to a horizontally-scrollable single-row strip (`flex-wrap: nowrap` + smaller cells) below 640px, instead of the desktop's wrapped multi-row block — its own scroll container, never the page body. **Follow-up correction:** the wrapper alone wasn't sufficient — `.heatmap-scroll` is a flex item of `.heatmap-panel` (a `.stack`), and without its own `min-width: 0` + explicit `width: 100%` it stretched to `.heatmap-grid`'s intrinsic nowrap content width (~517px for 52 weeks) instead of being clamped to the panel's width, so `overflow-x: auto` never got a chance to clip. Confirmed via live Playwright measurement against the Cloudflare Pages preview (not local `astro preview`, per the note below) — `.heatmap-scroll`'s `clientWidth` now stays at the viewport-derived width while its `scrollWidth` (~517px) scrolls internally, and `getBoundingClientRect().right` never exceeds the page's `clientWidth`.

## Mobile overflow follow-up pass (post Phase-4 live audit)

A user-run 360px/320px overflow audit against LIVE (deployed) data — not the local dev sandbox — found regressions Phase 4's own verification missed, because Phase 4 checked local/seeded data at 360px only, not live data at 320px:

- **`.grid-2/-3/-4` mobile collapse was silently dead on every page, at every width:** this repo's `global.css` overrides `.grid-2/-3/-4` unlayered (added in Phase 4 to widen tracks to `minmax(0, 1fr)`) — but `@f0rbit/ui`'s own mobile collapse (`grid-template-columns: 1fr` at `max-width: 768px`) lives inside `@layer utilities`. Per the CSS Cascade Layers spec, **an unlayered rule always beats a layered rule, regardless of source order or specificity** — so the always-3-column unlayered override permanently shadowed the upstream mobile collapse, at every viewport width, not just wide ones. `/projects` never actually became a 1-column grid on mobile; it just happened to not overflow badly enough to notice at 360px with short seed-data names. Fixed by re-declaring the same `@media (max-width: 768px) { .grid-2, .grid-3, .grid-4 { grid-template-columns: 1fr; } }` collapse in `global.css` itself (still unlayered, so it now wins). **Rule going forward:** any time this repo adds an unlayered override for a class that also has upstream `@f0rbit/ui` responsive behavior, the media-query variant must be re-declared locally too — the unlayered override doesn't inherit the layered rule's breakpoints, it just replaces the whole rule at all widths.
- **`min-width: 0` + `overflow-wrap: anywhere`/`word-break: break-word` on TEXT NODES, not just grid tracks:** Phase 4's "grid overflow class of bug" note (above) was about `1fr` grid _tracks_ not shrinking below their content's min-content width. This pass found a related but distinct bug class: even with a track/flex-item correctly set to `minmax(0, 1fr)` or given `min-width: 0`, a single unbroken text run inside it (a project name with no spaces, a commit message with a long token/URL, a breadcrumb name) still won't wrap on its own — text only wraps at whitespace by default. Both fixes are required together: `min-width: 0` on the shrinkable ancestor (grid track, flex item, or row/stack child) so the box itself can shrink, _and_ `overflow-wrap: anywhere` (preferred over `word-break: break-word` in this codebase) on the actual text-bearing element so a long unbroken word inside that shrunk box wraps instead of overflowing it. Fixed at: `ProjectCard.astro`'s `.project-card-name`, `ProjectPage.astro`'s `.project-breadcrumb`/`.project-article`, `CommitList.astro`'s `.commit-entry-message` (plus a new `.commit-list-entries` class on the message column so it can carry `min-width: 0` — `.commit-list` is a `.row`/flex-row, so the automatic minimum size on the main axis applied there without it).
- **Flex rows with fixed/unshrinking siblings need `flex-wrap: wrap` too, not just `min-width: 0`:** two more overflow bugs were rows that don't wrap at all rather than a track-sizing issue — `ProjectPage.astro`'s `.project-header` (title block + GitHub/Live action buttons, `flex-shrink: 0`) and `blog/[group]/[slug].astro`'s `.post-meta`/new `.post-meta-group` (author/date/read-time/category badge). Both got `flex-wrap: wrap` (+ `row-gap` on the meta row) so content drops to additional lines at narrow widths instead of being pushed off-screen. Unconditional (not media-gated) — desktop content already fits on one line, so wrap never triggers there; verified via 1440px screenshot showing no visual change.
- **Verification method for this pass:** local `astro preview` doesn't work with the Cloudflare adapter (existing gotcha, see below) and there are no API creds locally, so every fix in this pass was verified with a standalone Playwright script driving the actual Cloudflare Pages branch preview (`https://<branch>-<repo>.workers.dev`), asserting `document.documentElement.scrollWidth <= clientWidth` and enumerating any element whose `getBoundingClientRect().right > clientWidth` at both 360px and 320px, for every route, after confirming the deployed build actually contains the new CSS (grep the page HTML/CSS bundle for a string unique to the fix — asset hashes alone aren't a reliable "is my commit live" signal since Astro's per-page inline `<style>` chunks don't always get a new hash in the shared bundle).

## Perf pass (Phase 5)

- **About-page hobby images — local vendoring vs remote `remotePatterns`:** `src/pages/about.astro`'s hobby cards hotlinked four third-party hosts (a stock-photo CDN, a squarespace CDN, a reddit media host, a council site) via a raw CSS `background-image: url(...)`. These are genuinely third-party assets we don't own, so the fix was `astro.config.mjs`'s `image.domains` allow-list + `astro:assets`' `<Image>` (explicit `width`/`height` to avoid layout shift), not downloading them into `src/assets/`. Only vendor a remote image locally if it's actually one of our own assets (nothing currently in this repo qualifies).
- **Blog-HTML cache key format:** `src/utils.ts`'s `get_blog_post_html(locals, group, slug, render)` wraps the `remark`/`remark-html` render of a blog post in the same `get_cached`/`cached_fetch` SWR infra every other provider call uses (`src/lib/cache.ts`, 600s TTL). Cache key is `` `blog-html:${group}:${slug}` `` — always include both group and slug in any new per-post cache key, since slugs aren't guaranteed unique across groups (devpad vs dev.to).
- **`set:html` for cached remark output:** `blog/[group]/[slug].astro` previously interpolated the raw `VFile` object returned by `remark().process(...)` directly as `{parsed}` — Astro's renderer only escapes plain `string` children (see `node_modules/astro/dist/runtime/server/render/any.js`), so a non-string object like `VFile` fell through to the raw-write branch and rendered unescaped by accident. Once the render result is cached, it has to be a JSON-serializable plain `string` (not a `VFile`), so the template now uses `<article set:html={html} />` explicitly. `src/components/projects/ProjectPage.astro` still does the old raw-`VFile`-interpolation pattern (out of scope for this phase) — if it's ever wrapped in a cache too, convert it to `set:html` at the same time.
- **Island hydration directive policy:** `client:idle` for an above-the-fold animation that's always in the initial viewport (e.g. `Typewriter` in `index.astro` — hydrates as soon as the main thread is free, no `IntersectionObserver` needed since it'd fire immediately anyway); `client:visible` for everything else that isn't needed before it scrolls into view (`Clamp`, `PublishTime`, `SkillBars`, `SkillDetail`, `Collapsible`). There should be zero `client:load` directives anywhere in `src` — `grep -rn "client:load" src` is the regression check.
- **`drizzle-orm` removed:** confirmed unused via `grep -rn "drizzle" src` before deleting it from `package.json` and running `bun install`. If a future feature needs an ORM, re-evaluate rather than assuming this was a placeholder for planned use — it had never been wired up.
- **Full perf report:** `docs/perf-ttfb.md` has the complete TTFB analysis — current SSR/cache architecture, what shipped in this initiative with impact, the prerender evaluation (all routes stay SSR — content is remote-API-driven), and a prioritized report-only recommendations table (ISR-style prerendering, CDN edge-caching, per-source TTL tuning, cache warming, OG-image caching, etc.).

That turned out wrong in practice: `.page-container` was applied _twice_ (outer shell wrapper **and** again on several pages' inner content), compounding the escalating padding and squishing content into a narrow column while the titlebar stayed comparatively wide. Fixed in the redesign polish pass — `.page-container` now lives solely on `.terminal-body`.

## Single content-width container (redesign polish pass)

- **The bug:** `.page-container` (`global.css`) used an escalating `padding-inline` scale (1rem → 2rem @640px → 8rem @1024px → 12rem @1280px → 26rem @1700px) and was applied **twice, nested**: once on the outer shell wrapper (`Page.astro`'s `.page-shell`, wrapping the whole `<TerminalWindow>`) and again on several pages' own inner content element (`index.astro`'s `<main>`, `timeline.astro`'s content `<div>`). The two escalating paddings compounded (e.g. 8rem + 8rem = 16rem inset per side at ≥1024px), crushing content into a narrow sliver while the titlebar — inset only once — read comparatively full-width.
- **The fix — exactly ONE content-width container, on `.terminal-body`:** `.page-container` (`global.css`) is now a single, non-escalating definition: `max-width: 64rem; margin-inline: auto; padding-inline: clamp(1rem, 4vw, 2.5rem);`. It is applied in exactly two places, both legitimate top-level (non-nested) usages:
  - `TerminalWindow.astro`'s `.terminal-body` (the actual content column under the titlebar) — `class="terminal-body page-container"`. `.terminal-body` itself keeps only `padding-block` (vertical spacing); all horizontal inset comes from `.page-container`.
  - `Footer.astro`'s inner wrapper — the footer sits _outside_ `.terminal-body`/`TerminalWindow` entirely (a sibling in `Page.astro`), so it needs its own instance of the same constraint to column-align with the body content above it.
  - `Page.astro`'s outer `.page-shell` (which wraps `<TerminalWindow>`) no longer carries `page-container` — it's full-bleed relative to the shell, so the titlebar (a `.terminal-window` child, sibling of `.terminal-body`) spans the full shell width, not the narrower content column.
  - `index.astro`'s `<main>` and `timeline.astro`'s content `<div>` had `page-container` **removed** — they were double-applying it on top of the (now single) `.terminal-body` instance. Keep `home-sections`/`timeline-page` etc. for their own flex/gap layout, but never re-add `page-container` to anything already rendered inside `<TerminalWindow>`'s slot.
  - **Rule going forward:** before adding `page-container` (or reproducing an equivalent max-width/margin-inline/padding-inline triplet) anywhere, `grep -rn "page-container" src` first. If the element is already inside `<TerminalWindow>` (i.e. inside a `<Page>`/`<Home>` layout's slot), it's already width-constrained by `.terminal-body` — don't add a second constraint.
  - **Superseded — the titlebar is no longer full-bleed.** The above described a transitional state where `.page-container` lived only on `.terminal-body`, leaving `.terminal-titlebar` full-width relative to `.page-shell`. That read wrong once the titlebar and body sat side by side: the dots/nav didn't line up with the content edges below. Fixed by moving the max-width constraint up one level, onto `.terminal-window` itself (`width: 100%; max-width: 64rem; margin-inline: auto;`) — the parent of both `.terminal-titlebar` and `.terminal-body`, so they now share one width and one center-line. `.terminal-body` dropped the `page-container` class (no more nested max-width) but kept its own `padding-inline: clamp(1rem, 4vw, 2.5rem)` for horizontal inset. `.terminal-titlebar` gained the identical `padding-inline: clamp(1rem, 4vw, 2.5rem)` (previously a flat `var(--space-md)`) so its dots/nav sit flush with the body content's left/right edges. Net effect: `.page-container` on `global.css` is now used only by `Footer.astro`'s wrapper (still a legitimate standalone instance, since the footer is a `Page.astro` sibling of `TerminalWindow`, not a descendant) — `TerminalWindow.astro` no longer references the `page-container` class at all, it reproduces the same three values locally split across `.terminal-window` (width) and `.terminal-body`/`.terminal-titlebar` (padding) so the titlebar can share the padding without inheriting a second max-width.
- **`64rem` max-width — how it was chosen:** compared against the redesign mockup's home two-column section and the projects/about 3–4-col grids (which need to breathe) vs. body paragraphs (which shouldn't stretch to absurd line lengths). `64rem` (1024px) is the same value that used to be the _first_ escalation tier of the old scale, keeps the home page's two-column `recent-columns` grid and the about/projects 3–4-col grids comfortably wide, and doesn't let single-column prose stretch unreasonably wide. If a future design pass wants a different column width, change it in exactly one place (`global.css`'s `.page-container`) — every consumer inherits it.
- **Pre-existing mobile overflow bugs found and fixed while verifying "no horizontal overflow at 360px" (unrelated to the container bug above, but in the same verification pass):**
  - `AboutMe.astro`'s `.about-left`/`.about-right` are CSS grid children of `.about-me` (`grid-template-columns: 1fr` below 1024px) with no `min-width: 0` — the classic grid-child-doesn't-shrink-below-content bug. Fixed with `min-width: 0` on both, plus a `max-width: 1023px` override that drops `.about-info`'s `width: max-content` to `width: 100%` and lets `.about-row` wrap (`.about-key`'s fixed `9rem` width plus a long `.about-value` like "University of Adelaide" doesn't fit combined with `max-content` sizing on narrow viewports).
  - `SkillCard.tsx` (Solid, used inside `SkillBars.tsx`'s `.grid.grid-3`) had a fixed-width skill-name span + 5 fixed-width bar chips + a label span in a non-wrapping flex row with no `min-width: 0` on the grid-item `<button>` — same class of bug, just in a Solid island instead of an Astro grid. Fixed with `min-width: 0` on the button and `flex-wrap: wrap` + `min-width: 0` on `SkillCard`'s root row.
  - `SkillDetail.tsx`'s experience-tag row uses `@f0rbit/ui`'s `.row`/`.row-sm` (which do **not** wrap by default — only `.cluster` does). A long tag list overflowed at narrow widths. Fixed with an inline `flex-wrap: wrap` on both rows rather than switching classes (keeps `.row`'s `align-items: center` semantics, just adds wrapping).
  - **Takeaway:** "no horizontal overflow" isn't guaranteed by fixing the outer container alone — any fixed-width flex/grid content (name columns, bar charts, tag lists) still needs its own `min-width: 0` / `flex-wrap: wrap` to actually shrink inside whatever container it ends up in. When verifying a layout fix at 360px, check `document.documentElement.scrollWidth > clientWidth` on every route, not just the one route the bug report named — these three were on `/about`, unrelated to the home-page container bug that prompted the check.

## Project detail + prose polish pass (post Phase 7)

- **Mobile sidebar reorder via `display: contents`:** `ProjectPage.astro`'s `.project-body` is a two-column grid on desktop (`minmax(0,1fr) 280px`, ≥1024px) with `.project-article` (README) first and `.project-sidebar` (an `<aside>` wrapping metadata card / stack / recent-commits) second. The mobile ask was to show the metadata card _before_ the README while keeping stack/commits _after_ it — i.e. a reorder that doesn't map onto the sidebar's own internal DOM order. Technique: under `max-width: 1023px`, set `.project-body { display: flex; flex-direction: column }` and `.project-sidebar { display: contents }` — `display: contents` unwraps the `<aside>` so its children (`.sidebar-box`, `.sidebar-stack`, `.sidebar-commits`) become direct flex items of `.project-body`, orderable alongside `.project-article` via the `order` property. The sidebar boxes keep their border/padding because those live on the boxes themselves (`.sidebar-box`), not on the now-unwrapped `.project-sidebar` wrapper. Desktop grid/markup is completely untouched — this only fires inside the mobile media query. Reuse this pattern any time a mobile reorder needs to interleave a wrapper's children with siblings outside that wrapper, rather than restructuring markup or duplicating components per-breakpoint.
- **Duplicate `Status` badge removed, not the layout wrapper:** `ProjectPage.astro` rendered `<Status>` twice (header, next to `<h1>`, and again in the metadata sidebar card) — kept the sidebar one (it's the canonical metadata location), removed the header one and collapsed `.project-heading` from a `row` (flex, gap, wrapping `h1`+badge) down to just `<h1 class="project-heading">` with the heading's own typography (font-size/weight/letter-spacing) moved onto that single selector. If a header-adjacent badge is ever wanted again, don't just add `<Status>` back next to a solo `h1` — re-add the flex row wrapper too.
- **Mobile action-button row:** `.project-actions` (GitHub / Live-or-Docs) is a vertical `stack stack-sm` on desktop (sits to the right of the title block). Under the same `max-width: 1023px` query it's overridden to `display: flex; flex-direction: row; width: 100%` with `.project-action { flex: 1; justify-content: center }` — full-width, equal-split, single row. This is a plain CSS override of the hardcoded desktop utility classes (`stack stack-sm`), not a class swap — Astro/CSS media queries can't conditionally swap classes, so overriding the rule inside the breakpoint is the correct approach here (confirmed against `@f0rbit/ui`'s own `.row`/`.stack` semantics via `llms.txt` before choosing this over reaching for a different primitive).
- **Prose word-spacing for the monospace body font:** `terminal.css`'s `body` rule uses `--font-mono` for everything (see "Terminal redesign" above — no webfont, pure system mono stack), which means every space renders as a full fixed-width character cell. This reads as too-loose inter-word spacing in actual prose (the AboutMe bio was the clearest example). Fixed with `word-spacing: -0.15ch` on `body`, tuned visually (screenshotted at 1200px against the live bio paragraph) — tight enough to read like normal prose kerning, not so tight words visually run together. **Must be reset to `normal`** on `pre`, `code`, `.specification pre`, `.specification code` — those rely on the font's fixed-width space for column/indentation alignment (Markdown code fences, the spec's rendered `<pre>`/`<code>`), and a negative word-spacing would silently misalign them. If the mono stack or this value ever changes, re-screenshot both a prose paragraph and a code block side by side — the two selectors moving out of sync is easy to miss since typecheck/build/lint don't catch a visual alignment regression.

If a future astro/TS upgrade fixes the upstream ambient-module collision, this cast can be deleted and `<Image>` restored — check via a throwaway probe file (`<Image src={x} alt="y" />` in a scratch page) before assuming it's fixed.
