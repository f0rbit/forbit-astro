# Cloudflare Cache Rule scoping doc

This is a **spec**, not an implementation. Applying a Cache Rule changes
production caching behavior for the whole zone and needs a human with
dashboard/account access — this doc exists so that action is a five-minute
copy-paste instead of a research task. See `docs/perf-ttfb.md` rec #3 for the
measurement that motivated this (every response, before and after the Phase B
`Cache-Control` header change, shows **no `cf-cache-status` header at all** —
Cloudflare is not edge-caching these routes today).

## 1. Why the `Cache-Control` header alone isn't enough

This site is `output: "server"` on `@astrojs/cloudflare` (`astro.config.mjs`) —
every HTML response is generated by the Worker at request time
(`src/pages/**/*.astro`, all `prerender = false`). That's fundamentally
different from Cloudflare's classic "cache my origin's static files" model:

- **Static assets** (the `assets` binding in `wrangler.jsonc`, i.e. the
  `dist/_astro/*` hashed JS/CSS bundle) are served directly by Cloudflare's
  Workers Assets layer, not through the Worker's `fetch` handler, and **are**
  edge-cached automatically — no rule needed, no `cf-cache-status` on those
  paths to worry about. Confirmed no explicit cache config exists for this in
  `wrangler.jsonc`/`astro.config.mjs`, which matches the "just works"
  contract Cloudflare documents for Workers Static Assets.
- **Worker-generated responses** (every `.astro` page, every `og/*.png`
  endpoint) are, by default, treated as **dynamic** content by Cloudflare's
  cache — the zone-level "Cache Everything" / default cache-level behavior
  that governs classic static-origin caching does not automatically extend
  to a Worker's own `fetch()` return value just because it carries a
  `Cache-Control: s-maxage=...` header. A **Cache Rule** (Rules → Cache
  Rules, the successor to legacy Page Rules) is the explicit mechanism that
  tells Cloudflare's edge "this URL pattern is eligible for cache" — without
  one, the response is served fresh from the Worker on every request
  (`cf-cache-status` absent = never entered the cache pipeline).
- Once a Cache Rule marks a path **"Eligible for cache,"** the rule's **Edge
  TTL** setting decides whether the edge then honors the origin's
  `Cache-Control` header or overrides it:
  - **"Use cache-control header if present, bypass cache if not"** /
    **"...use default Cloudflare behavior if not"** — edge TTL is driven by
    the Worker's own `s-maxage` (what this repo already emits). This is
    **"Respect origin"** in effect.
  - **"Ignore cache-control header and use this TTL"** — an explicit numeric
    Edge TTL overrides whatever the Worker sends, per rule.
  - `cf-cache-status` on a served response will read `MISS` (first request,
    origin fetched and cached), `HIT` (served from edge cache, Worker not
    invoked), `EXPIRED`/`REVALIDATED` (TTL passed, refetched), `DYNAMIC`
    (route matched but declared ineligible — e.g. `Bypass cache`), or
    `BYPASS` (rule explicitly bypasses). **`MISS` → `HIT` on a same-URL
    repeat request is the proof this actually worked** — see §5.

## 2. Exact rule(s) to create

Two rules, both "Eligible for cache" + **Respect origin's `s-maxage`**
(no Edge TTL override) — the Worker already emits the correct value per
route via `Cache-Control`, so let Cloudflare defer to it rather than
duplicating the number in two places (`src/utils.ts`'s `TTL_SECONDS` stays
the single source of truth).

| #   | Name                 | Matching expression                                                                                              | Cache eligibility  | Edge TTL                                           | Mirrors                                                                                 |
| --- | -------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------ | -------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 1   | `cache-detail-pages` | `(http.request.uri.path matches "^/projects/[^/]+$") or (http.request.uri.path matches "^/blog/[^/]+/[^/]+$")`   | Eligible for cache | Use cache-control header if present, bypass if not | `s-maxage=3600` (project) / `1800` (blog) — already set in-Worker                       |
| 2   | `cache-list-pages`   | `(http.request.uri.path eq "/projects") or (http.request.uri.path eq "/blog") or (http.request.uri.path eq "/")` | Eligible for cache | Use cache-control header if present, bypass if not | `s-maxage=300` — already set on `/projects`, `/blog`; **`/` has none today, see below** |

**`/` (home) and `/timeline` — decision:**

- `/` currently sets **no** `Cache-Control` header at all
  (`src/pages/index.astro` — confirmed via grep). Rule 2 above includes it in
  the match, but with no origin header the Edge TTL setting
  ("...bypass if not") means it stays uncached until a header is added.
  **Recommendation: add the same `s-maxage=300` header `/projects`/`/blog`
  already use** to `index.astro` in a follow-up code change (out of scope for
  this doc — it's a one-line addition matching the existing pattern at
  `src/pages/projects.astro:13`), then it's covered by rule 2 for free.
- `/timeline` is deliberately **excluded** from both rules — left dynamic.
  `docs/perf-ttfb.md` rec #1 already flags it as an unbounded render (no
  `limit`, thousands of commit rows against live data); caching a page whose
  render cost is the actual open problem just defers the fix, and its data
  (recent commits) is the freshest-changing content on the site (300s TTL on
  the in-Worker `timeline` cache already, per `TTL_SECONDS` in
  `src/utils.ts`) — caching it at the edge on top adds risk (stale commit
  history) for a route that's about to get its own scoping work anyway.
  Revisit once rec #1 lands.

## 3. Critical exclusions / risks

| Path                                                                        | Include in a Cache Rule?                                      | Reasoning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| --------------------------------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/og/*.png` (`src/pages/og/**`)                                             | **No new rule needed**                                        | `og_response()` (`src/lib/og-image.ts:71-81`) already sets its own `Cache-Control: public, max-age=86400` per response — that's a **plain `max-age`**, not `s-maxage`, so it's a valid signal for both edge and browser caching. A Cache Rule set to "respect origin" is harmless here (it would start honoring the existing header and edge-cache these too, which is a net win with near-zero risk — images, not per-visitor, already fully cacheable) but is **optional**, not required for this scoping doc's go/no-go. If pursued, add a third rule matching `^/og/.*\.png$`.           |
| `/_image` (Astro's image-proxy endpoint, used by `about.astro`'s `<Image>`) | **Exclude — do not add a rule**                               | Not audited in this pass; Astro's image endpoint response shape/headers weren't inspected, and getting this wrong (e.g. caching a broken/format-negotiated response keyed wrong) has a worse failure mode than leaving it dynamic. Revisit separately if `/about` becomes a caching priority.                                                                                                                                                                                                                                                                                                |
| `/_astro/*` (hashed JS/CSS)                                                 | **Already cached — no rule needed**                           | Served by Workers Static Assets (see §1), immutable-hashed filenames, confirmed no explicit cache config exists because none is needed — asset-layer caching is automatic and unrelated to Cache Rules (which only govern the Worker's own `fetch` responses).                                                                                                                                                                                                                                                                                                                               |
| Any route with per-visitor state (auth, cookies, personalization)           | **N/A today — explicit assumption, re-audit if this changes** | `docs/perf-ttfb.md` and the Phase B code comments both state "no per-visitor state on this route" for the pages carrying `Cache-Control` today. **This doc assumes the same holds for `/`, `/projects`, `/blog` list pages.** If auth, A/B testing, or any `Astro.cookies`/session read is ever added to a cached route, that route must be pulled out of the Cache Rule (or the rule must vary the cache key on the relevant cookie/header) before it ships — a shared edge cache serving one user's personalized response to another is a real data-leak class of bug, not a cosmetic one. |

**SWR interaction — two-layer TTL coherence:**

The in-Worker `get_cached`/`cached_fetch` (`src/lib/cache.ts`) SWR layer and
the proposed edge Cache Rule are **two independent caches in series**
(edge → Worker → upstream API), each with its own TTL:

- **Edge cache HIT** (within Edge TTL, which mirrors `s-maxage`): Cloudflare
  serves the cached HTML response directly. **The Worker does not run at
  all** — `get_cached`'s background SWR revalidation (`ctx.waitUntil`) never
  fires, because the Worker was never invoked. This is expected and fine:
  the edge's own `stale-while-revalidate=86400` directive covers this case —
  a request past `s-maxage` but within the `stale-while-revalidate` window
  gets the stale edge copy immediately while Cloudflare revalidates against
  the Worker in the background, which is the same UX contract the in-Worker
  layer provides, just one level up.
- **Edge cache MISS/EXPIRED**: the Worker runs, which is where the in-Worker
  SWR cache does its job exactly as it does today (`cf-cache-status: MISS` →
  Worker's own `cached_fetch` may itself HIT or trigger `safe_refresh`).
- **Coherence:** since the edge Edge TTL is set to **respect origin**
  (§2 — not an override), both layers share the same numeric TTL per route
  (3600 / 1800 / 300) by construction — there's only one place (`TTL_SECONDS`
  in `src/utils.ts`) that defines "how fresh," not two independently-tuned
  numbers to keep in sync. No re-tuning needed as designed. If a future
  change ever sets an **Edge TTL override** (ignoring origin headers)
  instead, that would introduce a second number to keep in sync manually —
  avoid that path unless there's a specific reason (e.g. CDN-side TTL needs
  to differ from browser-side `s-maxage`).
- **Net effect of adding the edge layer:** most requests within Edge TTL
  never reach the Worker at all — a `cf-cache-status: HIT` response has
  effectively zero TTFB cost. This is the actual "true edge offload" that
  Phase B's header alone did not deliver (see `docs/perf-ttfb.md`'s caveat).

## 4. How to apply it

### (a) Dashboard click-path

1. Cloudflare dashboard → select the `forbit.dev` zone → **Caching** →
   **Cache Rules** → **Create rule**.
2. Rule 1:
   - **Rule name:** `cache-detail-pages`
   - **When incoming requests match:** custom filter expression (paste):
     `(http.request.uri.path matches "^/projects/[^/]+$") or (http.request.uri.path matches "^/blog/[^/]+/[^/]+$")`
   - **Cache eligibility:** Eligible for cache
   - **Edge TTL:** Use cache-control header if present, bypass cache if not
   - Leave Browser TTL / Cache Key / everything else at default.
   - Deploy.
3. Rule 2 (add another rule, same ruleset or a new one):
   - **Rule name:** `cache-list-pages`
   - **When incoming requests match:**
     `(http.request.uri.path eq "/projects") or (http.request.uri.path eq "/blog") or (http.request.uri.path eq "/")`
   - Same **Cache eligibility** / **Edge TTL** settings as rule 1.
   - Deploy.
4. (Optional, low-risk) Rule 3 for `/og/*.png` — same settings, expression
   `http.request.uri.path matches "^/og/.*\.png$"`.

### (b) Worker Cache API via wrangler — cache the full SSR response in-Worker

**What a zone Cache Rule actually is, and why wrangler can't declare one.**
A Cloudflare Cache Rule is a **Rulesets-API object** — `phase =
"http_request_cache_settings"` on the zone, created via the dashboard, the
Cloudflare REST API, or an IaC tool that wraps that API. `wrangler.jsonc`
has no schema field for it (confirmed against
`node_modules/wrangler/config-schema.json` — no `rulesets`/`cache_rules`
key exists), and `wrangler` itself is a Workers deployment CLI, not a zone
config tool. **There is no `wrangler`-native way to declare a true zone
Cache Rule.**

What `wrangler` _can_ deploy is code that calls the **Workers Cache API**
(`caches.default` — the same primitive this repo already uses for
per-provider data, see `src/lib/cache.ts`'s `cached_fetch` /
`src/middleware.ts`'s `resolve_cache`). Applying it to the **whole HTML
`Response`**, not just provider JSON, in `src/middleware.ts` would look
like:

```ts
// src/middleware.ts — sketch, NOT implemented by this doc
const CACHEABLE_PATH = /^\/(projects(\/[^/]+)?|blog(\/[^/]+\/[^/]+)?)$/;

export const onRequest = defineMiddleware(async (context, next) => {
	// ...existing provider/cache wiring...
	const cache = resolve_cache(context.locals.runtime);
	const url = new URL(context.request.url);

	if (cache && context.request.method === "GET" && CACHEABLE_PATH.test(url.pathname)) {
		const key = new Request(url.toString()); // per-URL key, not per-provider-call
		const hit = await cache.match(key);
		if (hit) return hit;

		const response = await next();
		if (response.status === 200 && response.headers.get("Cache-Control")) {
			context.locals.ctx.waitUntil(cache.put(key, response.clone()));
		}
		return response;
	}

	return next();
});
```

Points that matter if this path is chosen:

- **Two layers, not a replacement.** This sits _above_ the existing
  `get_cached`/`cached_fetch` per-provider cache, not instead of it. Full
  hierarchy becomes: full-page Worker-cache MISS → Worker runs →
  `get_project_html`/`get_blog_post_html`/provider calls hit their own SWR
  cache (usually a HIT) → HTML assembled → both caches populated. This is
  coherent (nothing conflicts), but it's two independent TTL surfaces to
  reason about instead of one.
- **Cache key strategy.** Mirror `build_key` in `src/lib/cache.ts` — key on
  `` `https://cache.local/${BUILD_SHA}/${url.pathname}` `` (or similar) so a
  deploy busts the full-page cache exactly the way it already busts the
  data cache, rather than serving a stale page shell against a new build's
  assets/markup.
- **TTLs already exist — reuse, don't reinvent.** The per-route
  `Cache-Control: s-maxage=<3600|1800|300>` headers already set in
  `src/pages/projects/[project_id].astro` and
  `src/pages/blog/[group]/[slug].astro` are exactly what this middleware
  would key its own in-memory TTL check off (or, simpler, just trust
  `cache.put`'s own `Cache-Control`-driven expiry — the Workers Cache API
  honors the stored response's own `Cache-Control` header for eviction).
  `TTL_SECONDS` in `src/utils.ts` stays the single source of truth either
  way.
- **What must stay excluded.** Same exclusion list as §3: `/timeline` (no
  `Cache-Control` header today, and its render cost is the actual open
  problem), `/_image` (Astro's image-proxy — response shape not audited),
  `/og/*.png` (already self-cached by `og_response()`, no need to double up
  in middleware). `CACHEABLE_PATH` above only matches the two route
  families §2 already scoped. No per-visitor state today (same explicit
  assumption as §3) — re-audit before caching any route that gains
  auth/cookies/personalization.
- **The honest gain analysis — this is the sharp edge.** Caching the full
  HTML `Response` inside the Worker still **invokes the Worker** on every
  request (`onRequest` runs, `cache.match` is checked, the Worker pays its
  own cold/warm invocation cost) — unlike a true zone Cache Rule, which
  serves the cached response **without invoking the Worker at all**
  (`cf-cache-status: HIT` with zero Worker execution). Given `docs/perf-ttfb.md`'s
  own measurement — `/projects/devpad` browser-nav TTFB already dropped to
  ~18-23ms from the in-Worker **data** cache alone (recs #4/#5) — the
  _incremental_ win from also skipping remark re-render + the
  `get_project_html`/`get_blog_post_html` cache lookup (both already fast
  in-memory-equivalent operations) is small. **Be honest: for this site's
  traffic level, the marginal gain of Worker Cache API over the status quo
  is real but small — most of the TTFB win is already banked by the
  existing per-provider SWR cache.** The only case where this path clearly
  pays for itself is if Worker invocation count/cost itself becomes a
  concern (billed requests, CPU time) — not likely at personal-site
  traffic.

### (c) Alchemy `Ruleset` — a true zone Cache Rule, IaC-declared

**Alchemy does support this.** `alchemy/cloudflare` exports a generic
`Ruleset(id, props)` resource (source:
`alchemy/src/cloudflare/ruleset.ts` in the `sam-goodwin/alchemy` repo,
docs: `https://alchemy.run/providers/cloudflare/ruleset/ruleset/`) that
`PUT`s `/zones/{zoneId}/rulesets/phases/{phase}/entrypoint` — the exact
Rulesets-API endpoint a Cache Rule lives at. Its `phase` field is typed
`RulePhase`, whose union explicitly includes
`"http_request_cache_settings"` (`rule.ts`), and its `Rule` union includes
`SetCacheSettingsRule` (`action: "set_cache_settings"`, with
`action_parameters.cache: boolean` and `action_parameters.edge_ttl: {
mode: "respect_origin" | "override_origin" | "bypass_by_default", ... }`)
— a 1:1 typed mirror of the dashboard/API cache-settings action used in §2.
This is a real, typed, purpose-built resource — not a generic raw-API
escape hatch.

```ts
// infra.ts — sketch, NOT implemented by this doc; this repo has no infra.ts today
import alchemy from "alchemy";
import { Ruleset } from "alchemy/cloudflare";

const app = await alchemy("forbit-astro");

await Ruleset("cache-rules", {
	zone: "forbit.dev",
	phase: "http_request_cache_settings",
	rules: [
		{
			description: "cache-detail-pages",
			expression:
				'(http.request.uri.path matches "^/projects/[^/]+$") or (http.request.uri.path matches "^/blog/[^/]+/[^/]+$")',
			action: "set_cache_settings",
			action_parameters: { cache: true, edge_ttl: { mode: "respect_origin" } },
		},
		{
			description: "cache-list-pages",
			expression:
				'(http.request.uri.path eq "/projects") or (http.request.uri.path eq "/blog") or (http.request.uri.path eq "/")',
			action: "set_cache_settings",
			action_parameters: { cache: true, edge_ttl: { mode: "respect_origin" } },
		},
	],
});

await app.finalize();
```

Notes if this path is chosen:

- **This is a real zone Cache Rule** — identical mechanism to §2/§4a, just
  declared in code instead of clicked in the dashboard. No Worker
  invocation on a cache HIT (`cf-cache-status: HIT` served entirely at the
  edge) — this is the "true edge offload" `docs/perf-ttfb.md`'s caveat was
  asking for, unlike (b) above.
- **This repo has no IaC file today.** Per this repo's own `AGENTS.md`
  ("Infra file ignores"), `infra.ts`/`pipeline.ts`/`grants.ts` don't exist
  here. Choosing this path means introducing the **first** IaC file in
  this repo: `infra.ts` (per the `alchemy.run` shape used elsewhere in the
  user's devpad/pipelines stack — see the `pipelines-setup` skill), wiring
  `bunx alchemy deploy ./infra.ts` into a deploy step, and configuring an
  Alchemy OAuth profile (`bunx alchemy configure` — does not inherit
  `wrangler login`). `Ruleset` needs zone-level API permissions on
  whatever Cloudflare credential Alchemy runs as (`Zone > Cache Rules >
Edit` at minimum) — narrower than the account-wide credential this site
  otherwise doesn't need.
- **Idempotent by construction, but overwrites the whole phase.**
  `Ruleset`'s `updateRuleset` call replaces the **entire**
  `http_request_cache_settings` entrypoint ruleset for the zone on every
  deploy — fine here (nothing else uses that phase on `forbit.dev` today,
  confirmed by this doc's own §2/§4a being the first rules proposed for
  it), but a footgun if any other tool or the dashboard is ever used to
  add a third cache rule out-of-band — the next Alchemy deploy would
  silently delete it.

### Which to use for this repo

Neither is clearly "better" in the abstract — they trade off differently:

|                                       | Worker Cache API (b)                                                  | Alchemy `Ruleset` (c)                                                  |
| ------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Skips Worker invocation on a HIT      | No — Worker still runs                                                | Yes — true edge offload                                                |
| New infra needed                      | None — code change in an existing file                                | First IaC file in this repo (`infra.ts` + Alchemy setup)               |
| Deploy path                           | Existing `wrangler`/CI pipeline                                       | New: `bunx alchemy deploy` step                                        |
| Blast radius if wrong                 | Scoped to this repo's own middleware                                  | Zone-wide cache phase, deployed outside this repo's normal review path |
| Matches existing pattern in this repo | Yes — same `caches.default` primitive `src/lib/cache.ts` already uses | No — net-new tool for a single-file, non-platform site                 |

**Recommendation: Alchemy `Ruleset`, not the Worker Cache API — but only if
the IaC overhead is wanted at all; otherwise the dashboard (§4a) remains
the pragmatic default.** Reasoning in one line: the Worker Cache API (b)
doesn't actually solve the problem this doc exists for (per
`docs/perf-ttfb.md`'s caveat — "Cloudflare is not edge-caching these
routes today," meaning the Worker isn't skipped) and its win over the
already-banked in-Worker data-cache TTFB is small per the honest analysis
above, whereas Alchemy's `Ruleset` produces the exact same artifact as the
dashboard path (a real zone Cache Rule) with the added benefit of being
version-controlled and reproducible. The **first** IaC file in a
previously-IaC-free repo is real overhead, though, and this site is a
personal portfolio, not a platform service — if that overhead isn't
wanted, **§4a (dashboard) is still the lowest-effort correct choice** and
delivers the identical runtime behavior as (c), just without the
version-controlled deploy story.

## 5. Verification plan

After applying (either path), from a shell with network access to
production:

```bash
# First hit — expect MISS (or nothing cached yet)
curl -sI https://forbit.dev/projects/devpad | grep -i "cf-cache-status\|cache-control\|age:"

# Immediately repeat — expect HIT, age: should be small and non-zero
curl -sI https://forbit.dev/projects/devpad | grep -i "cf-cache-status\|cache-control\|age:"

# Repeat once more a few seconds later — age: should have incremented
curl -sI https://forbit.dev/projects/devpad | grep -i "cf-cache-status\|cache-control\|age:"

# Same for a blog post and a list page
curl -sI https://forbit.dev/blog/dev/vibe-coding-slot-machine | grep -i "cf-cache-status\|cache-control\|age:"
curl -sI https://forbit.dev/projects | grep -i "cf-cache-status\|cache-control\|age:"
```

Look for:

- `cf-cache-status: MISS` on the first request to a not-recently-hit URL,
  `cf-cache-status: HIT` on the immediate repeat.
- `age:` present and incrementing across repeat requests (proves the edge
  is serving from cache, not re-fetching the Worker each time).
- `cache-control` unchanged from what the Worker already sends (confirms
  "respect origin" is working as configured, not silently overridden).
- **`/timeline` and `/_image`** should continue to show **no**
  `cf-cache-status` header (or `DYNAMIC`) — confirms the exclusions held.

Then **re-measure TTFB** the same way Phase B did (`docs/perf-ttfb.md`'s
"Before/after measurement" table): 3 warm `curl -sI` TTFB samples plus the
Playwright browser-nav-timing fallback (`lighthouse_audit` has no
performance category available in this environment, per that doc), for
`/projects/devpad` and the blog post used before, so the new numbers are
directly comparable to the existing before/after table rather than a fresh
unrelated measurement.

## 6. Recommendation: go / no-go

**Go — but low urgency, and scoped exactly to the two rules in §2.**

Reasoning:

- **Traffic level:** this is a personal portfolio/blog site, not a
  high-traffic product — the in-Worker SWR cache (`get_cached`/`cached_fetch`,
  600s-ish TTLs) already eliminates the dominant cost (upstream API
  latency) for the vast majority of requests, and Phase B's measurement
  showed the project-detail route already dropped to ~20ms browser-nav
  TTFB from the in-Worker cache alone. The _incremental_ win from also
  skipping the Worker invocation entirely (true edge HIT) is real but
  smaller in absolute terms than the win already banked.
- **Blast radius is small and well-understood:** two rules, both
  "respect origin" (no new TTL number to maintain), both scoped to routes
  already confirmed to carry no per-visitor state, with `/timeline` and
  `/_image` explicitly excluded pending further work. This is a low-risk,
  low-effort change (five minutes in the dashboard) for a genuine
  (if secondary) TTFB improvement on the two highest-value cached routes.
- **Why not skip it entirely:** Phase B already did the work of adding
  correct `Cache-Control` headers and TTLs; leaving the Cache Rule
  unset means that work is only half-realized (the header exists but has
  no effect at the edge, per `docs/perf-ttfb.md`'s caveat) — for a
  five-minute dashboard action, closing that gap is worth doing.

**If go: apply exactly rule 1 + rule 2 from §2, via Alchemy's `Ruleset`
(§4c) if the IaC overhead is wanted, otherwise the dashboard (§4a) — skip
the Worker Cache API path (§4b, doesn't solve the "Worker still invoked"
problem) and the optional OG-image rule unless a future need justifies
them, then run the §5 verification + re-measurement.**
