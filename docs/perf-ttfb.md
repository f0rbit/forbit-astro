# TTFB / performance report

This is a written analysis of the site's time-to-first-byte and client
performance posture. It separates what was **shipped** as part of this
initiative from what is **report-only** — a set of prioritized
recommendations that were evaluated but not implemented.

## Current architecture

- Full SSR on Cloudflare Workers via `@astrojs/cloudflare` (`astro.config.mjs`,
  `output: "server"`). Every route in `src/pages/` sets (or inherits)
  `prerender = false` — see `src/pages/index.astro:12`,
  `src/pages/about.astro:37`, `src/pages/blog.astro:25`,
  `src/pages/blog/[group]/[slug].astro:34`, `src/pages/timeline.astro:8`,
  `src/pages/projects.astro:10`, and the three OG-image endpoints under
  `src/pages/og/`. `src/pages/projects/[project_id].astro` has no explicit
  flag and inherits the same server-rendered default.
- All page data comes from remote APIs through the Provider pattern
  (`src/providers/devpad.ts`, `src/providers/devto.ts`,
  `src/providers/posts-feed.ts`), wired into `Astro.locals.providers` by
  `src/middleware.ts`'s `onRequest`.
- The single TTFB lever already in place is the SWR edge cache:
  `src/lib/cache.ts`'s `cached_fetch`, backed by the Workers Cache API
  (`context.locals.runtime.caches.default`, resolved in
  `src/middleware.ts:resolve_cache`). `src/utils.ts:27` (`get_cached`) wraps
  every provider call with a **600-second TTL**
  (`DEFAULT_TTL_SECONDS = 10 * 60` at `src/utils.ts:7`) and stale-while-
  revalidate semantics: a cache hit within TTL returns immediately
  (`src/lib/cache.ts:53`); a hit past TTL still returns the stale value but
  kicks off `ctx.waitUntil(safe_refresh(...))` in the background
  (`src/lib/cache.ts:56`) so the _next_ request gets fresh data without the
  requesting user paying the upstream latency. Because content is
  remote-API-driven, TTFB on an actual cache miss is dominated by upstream
  API latency (devpad, dev.to, the posts-feed), not by Astro/Workers
  overhead.

## Shipped this initiative (with impact)

- **moment.js removed.** `src/lib/time.ts` replaces moment with native `Intl`
  - ms-math (`format_duration`, `format_relative_time`, `format_calendar`,
    `format_full_date_time`), re-exported from `src/utils.ts`. This was landed
    in an earlier phase of this redesign (see `AGENTS.md`'s "Dates — moment.js
    removed" entry) — `PublishTime.tsx`, a hydrated Solid island, no longer
    ships moment to the client. The current build's island chunks are small
    and moment-free: `dist/_astro/PublishTime.Bt9zUcm6.js` is 2.43 kB
    (gzip 1.00 kB) and a second `PublishTime.DScP12NG.js` split is 0.10 kB —
    no pre-removal baseline was captured at the time, so an exact before/after
    delta can't be quantified here, but moment alone is typically 15-20 kB
    gzipped, so removing it from a client bundle this size is a meaningful
    proportional win.
- **Blog-post HTML caching (`src/pages/blog/[group]/[slug].astro`).**
  Previously, `remark().use(remarkHtml).process(post.content)` ran at
  request time on every hit (`src/pages/blog/[group]/[slug].astro:16`,
  pre-change). It now runs through `get_blog_post_html` in `src/utils.ts`,
  which reuses the _same_ `get_cached`/`cached_fetch` SWR infra as every
  other provider call (no bespoke cache mechanism) with cache key
  `blog-html:<group>:<slug>` — group and slug are both part of the key, so
  two posts can never collide. Within the 600s TTL, a repeat request to the
  same post skips the remark parse entirely and serves the cached HTML
  string; past the TTL, the cache still serves the stale HTML while
  revalidating in the background, matching the existing SWR behavior for
  post data. `src/components/projects/ProjectPage.astro` also runs a remark
  render per request (`ProjectPage.astro:19`, project specification
  markdown) — it was **not** wrapped in this task's scope (see report-only
  recommendations below).
- **Images moved to `astro:assets`.** The `/about` hobby cards
  (`src/pages/about.astro`) previously set `background-image: url(...)`
  directly to four third-party hosts (a stock-photo CDN, a squarespace CDN,
  a reddit media host, a council site) — a render-time hotlink with no
  resizing/format negotiation. They're genuinely third-party assets (not
  ours to vendor), so the fix was `astro.config.mjs`'s new `image.domains`
  allow-list plus Astro's `<Image>` component, which serves them resized
  (`width={480} height={336}`) and re-encoded as webp through the `/_image`
  endpoint (verified locally: `GET /_image?...&f=webp` returns
  `200 image/jpeg` — Sharp isn't available under the Cloudflare adapter, so
  the fallback image service still serves a valid, correctly-sized image).
  Fixed dimensions on `<Image>` also eliminate layout shift for these cards
  (no more waiting on a background image to paint before the card has a
  height). `Navigation.astro` (the forbit-icon/logo concern this task
  anticipated) does not currently render any image — Phase 3's redesign
  replaced the visual logo with the text-based `path-nav` tab strip (see
  `AGENTS.md`'s terminal-redesign section) — so there was no `<img>` left to
  convert there; `src/assets/forbit-icon.png` is an unused leftover asset,
  noted but not deleted in this pass to keep the diff scoped to the plan.
- **`drizzle-orm` removed.** Confirmed unused via `grep -rn "drizzle" src`
  (no matches) before removing the dependency from `package.json` and
  running `bun install` to update `bun.lock`. This trims install size and
  the dependency graph Wrangler has to bundle/type-check, though it has no
  runtime TTFB impact since it was never imported.
- **Island hydration tuned to visible/idle.** Every remaining
  `client:load` was audited and changed:
  - `src/components/about/ExperienceCard.astro` — `Clamp` (`client:load` →
    `client:visible`; it's below the fold in the experience timeline).
  - `src/components/projects/ProjectPage.astro` — `PublishTime`
    (`client:load` → `client:visible`; it's in the project detail sidebar,
    below the fold on first paint).
  - `src/pages/index.astro` — `Typewriter` (`client:visible` →
    `client:idle`; it's the home-page hero, always in the initial viewport,
    so `client:idle` hydrates as soon as the main thread is free instead of
    paying for an `IntersectionObserver` that would fire immediately
    anyway).
    All other islands (`SkillSelector` in `src/pages/about.astro`,
    `PublishTime` in `src/components/blog/BlogCard.astro` and
    `src/pages/blog/[group]/[slug].astro`, `Collapsible` in
    `src/components/activity/Timeline.astro`) were already `client:visible`.
    **After this change there are zero `client:load` directives left in the
    codebase** (`grep -rn "client:load" src` returns no matches).

## Prerender evaluation (Task 5.2, item 2)

Every route was checked against `prerender`. All of them read from
`Astro.locals.providers` (devpad/dev.to/posts-feed) at request time, so
their content changes whenever those upstream sources change — none is
genuinely static. `prerender = true` was **not** applied to any route; all
routes remain SSR and lean on the SWR cache described above. This is a
deliberate "no risky change" call, not an oversight — see the recommendation
below for a narrower, later path to partial pre-rendering.
